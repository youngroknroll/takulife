# takulife

서브컬처 팬을 위한 컬렉션-퍼스트 웹 서비스. 공식 이벤트를 발견하고, 다녀온 경험을 기록하고, 보유·구함·교환 의사가 있는 굿즈를 아카이빙하는 흐름을 하나로 연결한다. 1인 프로젝트로 설계부터 구현, 검증까지 직접 진행했다.

**상태**: 배포 준비는 끝났지만 아직 배포하지 않았다(미배포). 아래 "현재 상태와 한계"에 정직하게 남겨둔다.

## 주요 기능

- **이벤트 카탈로그**: 목록·달력·상세 페이지, 상태(예정/진행/종료 임박/종료)·지역·카테고리 필터, 라이브 검색 요약, 등록 후 시간이 지난 정보에 대한 재검증 경고(D-7)
- **개인 아카이브**: 찜, 방문 예정, 방문 기록(기록당 최대 5장 사진 업로드, 업로드 멱등 키로 재시도 중복 방지), 활동 달력, 나의 일정, 비공식 개인 항목(`PersonalEntry`) 등록
- **컬렉션**: 보유/구함/교환 의사를 서로 독립된 3축으로 관리하는 `CollectionItem`, 컬렉션-퍼스트 홈 화면
- **공식 제보**: 사용자가 비공식 개인 항목을 공식 URL과 함께 제보하면 관리자 검수(draft) 파이프라인을 거쳐야만 공개된다
- **인증**: 이메일 가입과 인증 필수, 비밀번호 재설정, 로그인 시도 잠금(django-axes), 탈퇴 10일 유예, 계정 설정
- **스태프 콘솔**: 이벤트 CRUD, 검수 큐, 대시보드(CSS 전용 시각화) — 소비자 화면과 완전히 분리
- **API 문서**: drf-spectacular 기반 OpenAPI 스키마와 Swagger UI(`/api/docs/`) 자체 서빙
- **전면 에디토리얼 리디자인**: 타이포그래피 중심 디자인, 다크모드, 접근성(ARIA, inert 기반 포커스 제어, WCAG 2.2.2 자동재생 정지 대응)

## 아키텍처

Django 앱 8개로 도메인을 분리하고, 프레젠테이션 계층을 별도 앱(`web`)으로 떼어내 앱 간 순환 의존을 완전히 제거했다(경계를 넘나드는 3쌍의 순환 참조 → 0, 완전 DAG). 이 경계는 문서가 아니라 아키텍처 가드 테스트로 강제한다.

- `accounts`: 인증과 계정 생명주기 (가입, 이메일 인증, 소셜 로그인, 탈퇴)
- `events`: 공개된(published) 이벤트 — 목록, 달력, 상세, 필터, API
- `drafts`: 공개 전 단계 — URL 기반 초안 생성, 관리자 검수·승인·반려 워크플로
- `archive`: 개인 상태(찜, 방문 예정/기록)와 컬렉션(`CollectionItem`) 도메인
- `staff`: 스태프 콘솔 — 이벤트 CRUD, 검수 큐, 대시보드
- `core`: 여러 앱이 공유하는 쿼리, 서비스, LLM 어댑터 등 횡단 관심사
- `web`: 소비자용 화면 라우팅과 뷰(프레젠테이션 전용 계층)
- `config`: Django 설정과 루트 라우팅

## 로컬 실행

```bash
cp .env.example .env
uv sync
uv run python manage.py migrate
uv run python manage.py runserver
```

- DB: `DATABASE_URL`을 비워두면 SQLite로 폴백한다(로컬 기본값). PostgreSQL을 쓰려면 `docker compose up -d db` 후 `.env`에 `DATABASE_URL=postgresql://taku:taku@localhost:5432/taku`를 설정한다.
- 이메일: `EMAIL_HOST`를 비워두면 콘솔 백엔드로 동작한다(로컬에서 SMTP 없이 인증 메일 내용을 터미널에서 확인 가능).
- 테스트: `uv run pytest -q`

## 엔지니어링 하이라이트

- **아키텍처 경계를 테스트로 강제**: 프레젠테이션 계층(`web`)을 분리해 앱 순환 의존을 3쌍에서 0으로 없애고, 파일시스템 유도 스캔 기반 경계 가드 테스트를 도입했다. 금지된 임포트를 일부러 26회 주입하는 뮤테이션 검증으로 가드가 실제로 걸리는지 전부 확인했다(2026-08 실측).
- **뮤테이션 기반 테스트 검증**: 테스트를 작성한 뒤 코드를 의도적으로 깨서(mutation) 실패하는지 상시 확인하는 습관을 들였다. 이 과정에서 "통과는 하지만 실제로는 아무것도 검증하지 않는" 무력한 테스트를 여러 차례 적발하고 교체했다.
- **브라우저 실측 이중 리뷰**: 자동 테스트 범위를 백엔드 로직으로 명확히 제한하는 대신, 프런트엔드는 Chrome DevTools 프로토콜로 접근성 트리·탭 순서·320~1200px 5개 폭·라이트/다크 모드·reduced-motion을 직접 측정하는 검증 절차를 만들었다.
- **테스트 스위트 성능 개선**: 313초 걸리던 스위트를 27초로 단축했다(2026-07 실측).
- **업로드 멱등성**: 방문 기록 사진 업로드에 `client_token`을 도입해 네트워크 재시도로 인한 중복 업로드를 방지했다.
- **동시성·남용 방지**: `select_for_update` 행 잠금, DRF 스로틀 스코프 7종, "교환 가능 수량은 보유 수량을 넘을 수 없다" 같은 도메인 불변식을 DB `CheckConstraint`까지 내려서 강제했다.
- **CI에서 실제 컨테이너 기동 스모크**: Docker 이미지를 빌드해 실제로 띄운 뒤 `/api/health/`를 폴링하는 스모크 테스트를 CI에 포함했다.

## 설계 서사: 왜 관리자 검수 파이프라인인가

서브컬처 오프라인 이벤트 정보(공식 홈페이지, X, 협업 카페 공지, 팝업 스토어 공지 등)는 이미 여러 채널에 존재한다. 이 프로젝트가 정의한 문제는 정보의 부재가 아니라 **정보의 분산**이었다 — 사용자는 관심 있는 이벤트를 찾기 위해 매번 여러 채널을 다시 탐색하고, 찾은 뒤에도 그것이 실제 공식 정보인지 다시 검증해야 한다. 이 반복되는 탐색 비용과 검증 비용이 진짜 문제였다.

세 가지 옵션을 비교했다.

1. **링크 큐레이션**: 구현 비용이 낮지만 사용자가 결국 원문으로 다시 이동해야 해서 탐색 비용 감소 폭이 작고 검증 책임이 여전히 사용자에게 남는다.
2. **커뮤니티 제보**: 데이터를 빠르게 늘릴 수 있지만 초기 품질 관리 부담과 신뢰도 관리 어려움이 크고, 공식성 기준이 흐려질 위험이 있다.
3. **Official URL + Admin Review + Publish**: 공식 URL을 기준으로 초안을 생성하고, 추출 결과는 확정값이 아닌 후보값으로만 취급하며, 관리자 검수를 거친 뒤에만 게시한다. 구현 비용과 운영 단계는 늘지만 공개 정보의 신뢰성을 통제할 수 있다.

최종적으로 세 번째를 선택했다. 이유는 이 프로젝트의 핵심 문제가 수집량 부족이 아니라 신뢰 가능한 탐색 흐름의 부재였기 때문이다. 이 결정은 제품 구조 전반에 반영됐다 — `draft`(공개 전)와 `published event`(공개 후)를 명확히 분리하고, 관리자 승인 전에는 어떤 추출 결과도 공개하지 않으며, 동일 공식 URL의 중복 게시를 막는다. 사용자가 보는 것은 추출 결과가 아니라 항상 검수 결과다.

## 의도적으로 만들지 않은 것

- **커뮤니티 피드, 댓글, 메시지**: 범위 밖. 신뢰 가능한 공개 데이터 구조를 먼저 확보하는 것이 우선이었다.
- **결제, 배송, 에스크로, 판매/마켓플레이스**: 범위 밖. 애초에 이 서비스는 판매 플랫폼이 아니다.
- **추천 시스템**: 범위 밖.
- **교환 매칭**: 컬렉션의 "교환 의사 표시" 축까지는 구현했지만, 실제 사용자 간 매칭 기능은 밀도·신원 품질·프라이버시·신고·차단·모더레이션·운영 게이트가 승인되기 전까지는 착수하지 않는다.
- **제보의 무검수 즉시 공개**: 사용자가 제보한 정보라도 관리자 검수 파이프라인을 거치지 않고는 절대 공개되지 않는다.

한 가지는 정확히 구분해서 밝힌다. **LLM 기반 draft 자동 추출 파이프라인은 "안 만든" 것이 아니라 구현까지 끝냈고, 비용 정책(유료 LLM API 사용 제한)에 따라 기능 플래그로 꺼둔 채 동결한 상태**다.

## 현재 상태와 한계

- **미배포**: 애플리케이션과 CI는 배포 가능한 상태지만, 실제 배포에 필요한 인프라 계정 액션(도메인, PaaS, 관리형 DB 등)이 아직 남아 있어 실서비스로 올라가 있지 않다.
- **SMTP 미설정**: 실환경 이메일 발송 설정이 없어 실사용자 대상 이메일 인증이 아직 가동되지 않는다(로컬은 콘솔 백엔드로 동작 확인).
- **Google OAuth 미활성**: 소셜 로그인 코드와 UI는 존재하지만, OAuth 자격증명을 등록하지 않아 실제로는 비활성 상태다.
- **실사용자 0명**: 아직 실사용자에게 노출된 적이 없는, 개발·검증 단계의 프로젝트다.
