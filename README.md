# takulife

서브컬처 팬을 위한 컬렉션-퍼스트 웹 서비스입니다. 공식 이벤트를 발견하고, 다녀온 경험을 기록하고, 보유·구함·교환 의사가 있는 굿즈를 아카이빙하는 흐름을 하나로 연결합니다.

**상태**: 배포 준비는 끝났지만 아직 배포하지 않았습니다(미배포). 자세한 내용은 아래 "현재 상태와 한계"에 정직하게 남겨둡니다.

**기여 범위**: 팀 프로젝트가 아닌 1인 프로젝트로, 기획·도메인 설계·백엔드·프론트엔드·CI를 전부 직접 수행했습니다.

## 시스템 설계

### 저장소 구조

Django 앱 8개로 도메인을 분리했습니다 — `accounts`(인증·계정 생명주기), `events`(공개된 이벤트), `drafts`(공개 전 초안·검수 워크플로), `archive`(개인 기록·컬렉션), `staff`(스태프 콘솔), `core`(공유 쿼리·서비스·LLM 어댑터), `web`(소비자 화면 프레젠테이션 전용), `config`(설정·루트 라우팅).

프레젠테이션 계층을 `web` 앱으로 분리하면서 앱 간 순환 의존 3쌍을 0으로 만들었고(완전 DAG), 이 경계는 문서가 아니라 아키텍처 가드 테스트로 강제합니다.

### 요청 흐름

핵심 유스케이스인 방문 기록 사진 업로드로 설명합니다. `POST /api/visit-records/<record_id>/photos/` 요청은 DRF 뷰(`archive`, 세션 인증·소유자 검사·스로틀)를 거쳐 서비스 계층 `archive/services.py: create_visit_record_photo()`로 전달되고, 여기서 모델을 저장합니다.

서비스는 행 잠금(`select_for_update`) 안에서 사진 상한(기록당 5장) 검사와 멱등 replay 조회를 함께 수행하며, DB `UniqueConstraint`가 2차 방어선 역할을 합니다. 화면(SSR 템플릿)은 `web` 앱이 전담하고 JSON API는 도메인 앱(events/drafts/archive)이 제공해, 프레젠테이션과 도메인 계층을 분리했습니다. 비즈니스 규칙은 뷰가 아니라 서비스 함수와 모델에 둡니다.

### 데이터 정합성(DB 제약)

`archive/models.py`에 다음 제약이 실재합니다.

- `collectionitem_tradeable_lte_quantity`: 교환 가능 수량이 보유 수량을 넘지 않도록 CheckConstraint로 DB까지 강제합니다.
- `eventinterest_exactly_one_subject`: 찜은 공식 이벤트 또는 비공식 개인 항목 중 정확히 하나만 대상이 되도록(subject 패턴 정합성) CheckConstraint로 강제합니다.
- 조건부 UniqueConstraint(부분 유니크)로 (user, event)·(user, personal_entry) 중복 찜을 방지합니다.
- 다른 테이블 참조가 필요해 CheckConstraint로 내릴 수 없는 규칙은 서비스 계층에서 검증하고, 그 사유를 모델 주석에 남깁니다. "가능한 것은 DB로, 불가능한 것은 서비스로"라는 기준을 따릅니다.

모델 제약·인덱스 선언은 26건이며(2026-08-17 rg 정적 카운트), 그중 21건이 archive에 집중되어 있습니다.

### 동시성과 트랜잭션

`transaction.atomic`을 마이그레이션·테스트를 제외하고 36곳에서 사용해, 상태 변경을 서비스 계층에서 원자적으로 처리합니다. `select_for_update`는 6개 파일에서 사용하며, 사진 상한 검사·검수 승인·프로모션 등 동시 요청 경합 지점을 보호합니다(2026-08-17 rg 정적 카운트).

### 예외 처리와 로깅

도메인 예외(예: `PhotoLimitExceededError`)는 서비스가 던지고 뷰가 HTTP 상태 코드로 매핑합니다. 로깅은 stdout 콘솔 핸들러를 사용합니다(12-factor 방식 — PaaS 로그 수집을 전제). `django.request`는 ERROR 레벨로 남깁니다.

모니터링 진입점은 `/api/health/` 헬스 체크이며, CI Docker 스모크가 이 경로를 폴링합니다. 운영 지표는 아직 배포 전이라 없습니다.

### 배포 구조

Dockerfile과 entrypoint를 두어, 부팅 시 migrate를 실행하되 다중 인스턴스 환경에서는 env로 끄고 release-phase 명령을 쓰도록 설계했습니다. CI는 2-job 구성입니다 — `test`(PostgreSQL 서비스 컨테이너 + `manage.py check --deploy` 게이트), `docker`(이미지 빌드 후 실기동, `/api/health/` 폴링 스모크).

배포 프로파일에서는 HSTS·SSL 리다이렉트·secure 쿠키를 env로 전환합니다. django-axes 로그인 잠금은 신뢰 프록시 홉 수(`TRUSTED_PROXY_COUNT`) 기반으로 실제 클라이언트 IP를 판별해, 프록시 뒤에서 공격자 대신 프록시 IP가 잠겨 전원 잠금이 나는 오설정을 예방합니다.

## 트러블슈팅

### 1. 사진 업로드 멱등성: 재시도가 중복을 만들지 않게

**문제 상황**: 업로드 요청이 서버에 커밋된 뒤 응답만 유실되면, 클라이언트 재시도가 같은 사진을 중복 저장할 수 있었습니다. 외부 코드 검토는 작성 페이지의 실패 경로를 위험 지점으로 지목했습니다.

**원인 분석**: 코드를 추적해 보니 작성 페이지는 실패 시 재전송 채널 자체가 없었고, 실제 위험은 수정 페이지였습니다 — 실패 항목을 큐에 남겨 같은 File 객체를 다시 전송하는 경로였습니다. 검토 결과를 그대로 믿지 않고 재확인해서 찾은 것입니다. 또 하나, 기존 유사 패턴을 그대로 이식하면 상한 검사가 replay 조회보다 먼저 실행되어 "5장 상한을 채운 마지막 장의 재시도"가 멱등 응답 대신 상한 초과 오류로 거부되는 결함이 생긴다는 것을 서비스 코드를 읽다가 발견했습니다.

**해결 방법과 이유**: `(visit_record, client_token)` UniqueConstraint와 서비스의 replay 조회를 상한 검사와 같은 행 잠금 안에 배치해, DB 제약과 서비스 로직의 이중 방어를 만들었습니다. 멱등 토큰은 업로드 직전이 아니라 파일 선택 시점에 발급합니다 — 직전 발급이면 재시도마다 새 토큰이 생겨 코드는 멀쩡해 보여도 아무것도 막지 못하기 때문입니다.

**결과와 한계**: 제약 제거·replay 제거·검사 순서 역전, 이 세 가지 뮤테이션에서 각각 테스트가 실패하는 것을 확인했습니다. 브라우저에서 업로드가 커밋된 뒤 fetch 응답만 인위적으로 유실시키고 재시도해, 사진이 5장으로 유지되고(중복이었다면 6장) 두 요청이 같은 토큰을 싣는 것을 실측했습니다. 한계는 작성 페이지에 재시도 채널이 없어 토큰을 적용하지 않았고, 그 사유를 코드에 남겨두었다는 점입니다.

### 2. 테스트 스위트 313초에서 27초로, 그 과정에서 드러난 실결함

**문제 상황**: 백엔드 테스트 스위트가 313.81초 걸려 TDD의 Red-Green 루프를 사실상 막고 있었습니다.

**원인 분석**: 실행 시간을 뜯어 보니 테스트마다 프로덕션 강도의 비밀번호 해싱이 수행되고, 전역 autouse 캐시 초기화 픽스처가 모든 테스트에 걸려 있었으며, 빠른 단위 테스트와 느린 통합 테스트가 한 덩어리로 섞여 있었습니다.

**해결 방법과 이유**: 테스트 전용 설정(MD5 해셔)으로 해싱 비용을 제거하고, 테스트를 6계층 marker(unit/domain/web/contract/slow 등)로 분리했으며, 전역 autouse 픽스처를 제거했습니다.

**결과와 한계**: 27초대(약 9.4배 단축, 현재 25.66초 — 2026-08-18 실측)로 줄었습니다. 더 중요한 발견은, 전역 캐시 초기화를 제거하자 숨어 있던 실결함이 드러났다는 것입니다 — django-allauth의 기본 로그인 rate limit(30회/분/IP)이 성공한 로그인까지 카운트해, 연속 로그인 시나리오가 429로 실패했습니다. 전역 픽스처가 이 결함을 계속 가리고 있었던 셈입니다. 캐시 격리 픽스처로 해소하고, 이 계약을 고정하는 회귀 테스트(`tests/.../test_auth_rate_limit.py`)를 추가했습니다.

## 로컬 실행

```bash
cp .env.example .env
uv sync
uv run python manage.py migrate
uv run python manage.py runserver
```

- DB: `DATABASE_URL`을 비워두면 SQLite로 폴백합니다(로컬 기본값). PostgreSQL을 쓰려면 `docker compose up -d db` 후 `.env`에 `DATABASE_URL=postgresql://taku:taku@localhost:5432/taku`를 설정합니다.
- 이메일: `EMAIL_HOST`를 비워두면 콘솔 백엔드로 동작합니다(로컬에서 SMTP 없이 인증 메일 내용을 터미널에서 확인 가능).
- 테스트: `uv run pytest -q`

## 설계 서사: 왜 관리자 검수 파이프라인인가

서브컬처 오프라인 이벤트 정보는 이미 여러 채널(공식 홈페이지, X, 협업 카페 공지 등)에 존재합니다. 이 프로젝트가 정의한 문제는 정보의 부재가 아니라 **정보의 분산**이었습니다 — 사용자는 매번 여러 채널을 다시 탐색하고, 찾은 뒤에도 그것이 실제 공식 정보인지 다시 검증해야 합니다.

세 가지 옵션을 비교했습니다. 링크 큐레이션은 구현 비용이 낮지만 사용자가 결국 원문으로 다시 이동해야 해서 검증 책임이 여전히 사용자에게 남습니다. 커뮤니티 제보는 데이터를 빠르게 늘릴 수 있지만 초기 품질 관리 부담이 크고 공식성 기준이 흐려질 위험이 있습니다. Official URL + Admin Review + Publish 방식은 공식 URL을 기준으로 초안을 생성하고 추출 결과를 확정값이 아닌 후보값으로 취급하며, 관리자 검수를 거친 뒤에만 게시합니다.

최종적으로 세 번째를 선택했습니다. 핵심 문제가 수집량 부족이 아니라 신뢰 가능한 탐색 흐름의 부재였기 때문입니다. 이 결정은 제품 구조 전반에 반영되어, `draft`(공개 전)와 `published event`(공개 후)를 명확히 분리하고 관리자 승인 전에는 어떤 추출 결과도 공개하지 않으며 동일 공식 URL의 중복 게시를 막습니다. 사용자가 보는 것은 추출 결과가 아니라 항상 검수 결과입니다.

## 의도적으로 만들지 않은 것

- **커뮤니티 피드, 댓글, 메시지**: 범위 밖입니다. 신뢰 가능한 공개 데이터 구조를 먼저 확보하는 것이 우선이었습니다.
- **결제, 배송, 에스크로, 판매/마켓플레이스**: 범위 밖입니다. 애초에 이 서비스는 판매 플랫폼이 아닙니다.
- **추천 시스템**: 범위 밖입니다.
- **교환 매칭**: 컬렉션의 "교환 의사 표시" 축까지는 구현했지만, 실제 사용자 간 매칭 기능은 밀도·신원 품질·프라이버시·신고·차단·모더레이션·운영 게이트가 승인되기 전까지는 착수하지 않습니다.
- **제보의 무검수 즉시 공개**: 사용자가 제보한 정보라도 관리자 검수 파이프라인을 거치지 않고는 절대 공개되지 않습니다.

한 가지는 정확히 구분해서 밝힙니다. **LLM 기반 draft 자동 추출 파이프라인은 "안 만든" 것이 아니라 구현까지 끝냈고, 비용 정책(유료 LLM API 사용 제한)에 따라 기능 플래그로 꺼둔 채 동결한 상태**입니다.

## 현재 상태와 한계

- **미배포**: 애플리케이션과 CI는 배포 가능한 상태지만, 실제 배포에 필요한 인프라 계정 액션(도메인, PaaS, 관리형 DB 등)이 아직 남아 있어 실서비스로 올라가 있지 않습니다.
- **SMTP 미설정**: 실환경 이메일 발송 설정이 없어 실사용자 대상 이메일 인증이 아직 가동되지 않습니다(로컬은 콘솔 백엔드로 동작 확인).
- **Google OAuth 미활성**: 소셜 로그인 코드와 UI는 존재하지만, OAuth 자격증명을 등록하지 않아 실제로는 비활성 상태입니다.
- **실사용자 0명**: 아직 실사용자에게 노출된 적이 없는, 개발·검증 단계의 프로젝트입니다.
