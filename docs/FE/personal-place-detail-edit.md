# 비공식 장소 상세·수정 화면 — 구현 계약

**상태: 진행 중.** 브랜치 `feat/personal-place-detail-edit`, 커밋 1건(`8e65f2b`).
시안: claude.ai/design `22adfc05` / `비공식 장소 상세 페이지 (에디토리얼).dc.html`
(2026-07-30 취득). 두 화면이 한 파일에 있다.

이 문서는 **프론트 이중 게이트의 사전 산출물**이다. `AGENTS.md`가 요구하는
Frontend Review Evidence이며, 이것 없이 다시 구현하면 게이트를 다시 받아야 한다.

## 왜 이 화면인가

등록은 되는데 **열 수가 없었다.** 목록 행에 액션 5개가 몰려 있고 항목 자체로
들어가는 길이 없어, 사용자가 입력한 카테고리·참고 링크·메모가 쓰기 전용이었다.
수정 경로도 없어 오타 하나를 고치려면 삭제뿐이고, `personal_entry` FK가 찜·상태·
방문기록 3곳에서 `CASCADE`라 **그 장소에 딸린 방문 기록과 사진이 함께 사라진다.**
상세는 그 방문 기록 목록을 눈앞에 보여주는 화면이라 삭제 경고가 특히 중요하다.

## 사용자 확정 (2026-07-30)

1. 상세·수정을 **한 번에** 간다.
2. 삭제 확인 문구는 **목록과 동일** —
   `"이 항목을 삭제하시겠습니까? 연결된 찜·상태·방문 기록도 함께 삭제됩니다."`

## 화면 구조

### 상세 `/archive/personal/<id>/`
`← 직접 등록 목록으로` / 전역 오류 배너(`aria-live="polite"`) / 2열(≤45rem 단일)

**좌열** 사진 4:3(없으면 📍 + sr-only) · 좌상단 `🔒 나만 보기` 정적 필 ·
`♥ 찜` + 상태 필 · 전폭 `＋ 방문 기록 남기기` ·
`기록 정보` 3행(등록 / 마지막 수정 / 공개 범위="나만 보기" 상수)

**우열** 칩 행(카테고리 · 작품명 · `·` · `비공식 장소`) · h1 · `장소명 · 지역` +
`수정`/`삭제` · 메타 5행 · 메모 · 공식 제보 3상태 · `이 장소의 방문 기록 <n>`

### 수정 `/archive/personal/<id>/edit/`
`← 장소 상세로` / h1 `장소 정보 수정` + 부제 / 2열

**좌열** 사진 · `사진 교체`/`삭제` · `JPEG · PNG · WebP · 5MB 이하` · 🔒 안내 박스
**우열** 이름\* → `장소 정보` → 카테고리(칩 6 + 직접입력) → 작품명 →
장소명/지역 → `참고` → 참고 링크 → 메모 → 액션 바

## WED 이탈 판정 — 시안을 따르지 않는 곳

| # | 판정 | 근거 |
|---|---|---|
| 1 | **찜·상태 필을 청록으로 칠하지 않는다** | `controls.css`의 전역 컴포넌트. 시안대로 하면 **같은 상태가 목록과 상세에서 다른 색**이 된다 |
| 2 | `1.5px` → **`2px solid var(--text)`** | 저장소에 1.5px이 없고 브라우저가 1px로 반올림해 의도한 두께가 안 나온다 |
| 3 | 모바일 고정 바 = **`＋ 방문 기록 남기기` 단독** | 이 화면엔 핵심 루프 CTA가 있다. `수정`·`삭제`는 인플로우 |
| 4 | **수정 화면에도 삭제를 둔다** | 시안은 침묵하지만 `collection_edit`·`visit_edit` 관례. 침묵을 배제로 읽지 않는다 |
| 5 | 모바일에서 **`취소`를 숨기지 않는다** | `visit_edit.css`는 숨기지만 그 페이지만의 선례. 시안이 명시적으로 둘 다 요구 |
| 6 | 안전 여백 **`6rem`** | 6파일이 6rem, 2파일이 5rem. 다수 관례를 따른다 |
| 7 | 구분선은 `personal_create.html`의 `<h2>` 패턴 | 등록↔수정 시각 일치. `collection_edit`의 뱃지형 divider 금지 |
| 8 | 카테고리 칩 6개 = 시안·저장소 **일치**, 변경 없음 | `core/vocab.py::PERSONAL_ENTRY_CATEGORY_SUGGESTIONS` |
| 9 | 필드 순서·라벨 = 등록 폼과 **완전 동일** | 줄 단위 대조 완료 |
| 10 | 삭제 후 이동 = `/archive/personal/` | 형제 전부 "목록으로" 관례 |

**빈 값 처리**: 메모·참고 링크가 비면 "없음" 플레이스홀더를 만들지 말고
**섹션·행 자체를 생략**한다(`collection_detail` 관례).

## BIR 상호작용 기준

**절대 금지**
- `askConfirm`이 resolve되기 전에 어떤 상태도 disable/변경하지 마라 — 취소=부작용 0의 전제
- 찜 버튼에 `data-reload-on-success`를 붙이지 마라 (상태 필에는 붙인다)
- 사진 삭제를 메인 폼의 멀티파트 PATCH에 합치지 마라 — **별도 즉시 요청**
- 404 문구로 목록의 `"항목을 찾을 수 없습니다."`를 쓰지 마라 → `"이미 삭제된 항목입니다."`
- `visualViewport` 처리를 선제 추가하지 마라 (저장소 선례 0건)
- 고정 바 가시성에 새 메커니즘을 만들지 마라 — `cta_visibility.js` 재사용
- 수정 화면 `name` 속성 변경 금지 — `personal_create.js`가 `form.elements[...]`로 읽는다

**핵심 계약**
- **연타 가드**: 확인/검증 뒤, 첫 `await` 앞에 **동기적으로** `setLoading(btn, true)`.
  삭제·저장·제보·사진삭제 4개 컨트롤 전부.
- **404 잠금 캐스케이드**: 형제(`collection_detail.js`)는 `수정` 링크 1개만 잠갔다.
  이 페이지는 **찜·상태·제보·방문기록 CTA까지 5종 이상**을 함께 잠가야 한다.
  안 그러면 이미 없는 항목에 찜을 누른 사용자가 두 번째 막다른 골목을 만난다.
  상세는 상단 정적 링크에 `.focus()`만(새 링크 만들지 말 것),
  **수정은 그 링크마저 죽으므로 `collection.js`처럼 새 "목록으로 돌아가기" 링크 생성.**
- **PATCH 계약**: 폼의 모든 필드를 서버 렌더 값으로 채우고 **제출 시 전부 그대로 보낸다.**
  dirty 추적을 새로 만들지 마라 — 안 건드린 필드는 no-op, 지운 선택 필드는 `""`.
- **사진 삭제 = 즉시 반영** (`PATCH { image: null }`, JSON). 저장소의 다른 모든 단일
  클릭 파괴 동작이 즉시+확인이라 이것만 예외로 두면 확인창 동의와 어긋난다.
- **제보 성공(201)** → 목록이 아니라 **같은 상세 URL로 리로드**.
- `setLoading(btn, false)`가 `lockForm()`보다 **먼저** — bfcache 복원 시 `.is-loading`이
  남으면 전역 pageshow가 잠긴 버튼을 되살린다.
- 필수 항목 미입력 시 `.focus()` **호출한다** — `collection.js`는 안 하고
  `personal_create.js`는 한다. 접근성이 나은 쪽을 따른다.

**기존 것으로 안 되는 것 4가지**: 404 잠금 캐스케이드 확장 / 단일 이미지 삭제
(선례 없음) / 2버튼 고정 바(기존은 전부 1버튼) / 찜·상태·제보 동시 잠금 트리거.

**설계 결정**
- 방문 기록 조회는 **전용 함수 신설**(`list_visit_records_for_personal_entry`).
  `list_user_visit_records`에 인자를 더하지 마라 — 소비처 2곳에 영향이 간다.
  선례: `list_items_acquired_at_visit(visit)`가 같은 이유로 따로 만들어졌다.
- 소유자 격리는 **뷰 계층** `get_object_or_404(..., user=request.user)` (형제 2곳 동일).
- 수정 SSR 뷰는 **렌더만** 한다. 저장은 기존 DRF PATCH
  (`archive_collection_item_edit` 선례).
- `updated_at`은 SSR이 모델에서 직접 읽는다 — **직렬화기 변경 불필요**.
- 프라이버시: `_SubjectScopedPersonalEntryMixin`이 타인 항목 참조를 막지만
  **DB 제약이 아니라 직렬화기 계층 보장**이다. PD-9에서 user 필터를 넣을지 재판단.
