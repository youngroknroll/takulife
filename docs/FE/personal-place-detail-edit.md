## 왜 이 화면인가

등록은 되는데 **열 수가 없었다.** 목록 행에 액션 5개가 몰려 있고 항목 자체로
들어가는 길이 없어, 사용자가 입력한 카테고리·참고 링크·메모가 쓰기 전용이었다.
수정 경로도 없어 오타 하나를 고치려면 삭제뿐이고, `personal_entry` FK가 찜·상태·
방문기록 3곳에서 `CASCADE`라 **그 장소에 딸린 방문 기록과 사진이 함께 사라진다.**
상세는 그 방문 기록 목록을 눈앞에 보여주는 화면이라 삭제 경고가 특히 중요하다.

## 사용자 확정 (2026-07-30)

1. 상세·수정을 **한 번에** 간다.
2. 삭제 확인 문구는 **목록과 동일** —
   `"이 항목을 삭제하시겠습니까? 연결된 찜·상태·방문 기록도 함께 삭제됩니다."`

## BIR 상호작용 기준

**절대 금지**
- `askConfirm`이 resolve되기 전에 어떤 상태도 disable/변경하지 마라 — 취소=부작용 0의 전제
- 찜 버튼에 `data-reload-on-success`를 붙이지 마라 (상태 필에는 붙인다)
- 사진 삭제를 메인 폼의 멀티파트 PATCH에 합치지 마라 — **별도 즉시 요청**
- 404 문구로 목록의 `"항목을 찾을 수 없습니다."`를 쓰지 마라 → `"이미 삭제된 항목입니다."`
- `visualViewport` 처리를 선제 추가하지 마라 (저장소 선례 0건)
- 고정 바 가시성에 새 메커니즘을 만들지 마라 — `cta_visibility.js` 재사용
- 수정 화면 `name` 속성 변경 금지 — `personal_create.js`가 `form.elements[...]`로 읽는다

**핵심 계약**
- **연타 가드**: 확인/검증 뒤, 첫 `await` 앞에 **동기적으로** `setLoading(btn, true)`.
  삭제·저장·제보·사진삭제 4개 컨트롤 전부.
- **404 잠금 캐스케이드**: 형제(`collection_detail.js`)는 `수정` 링크 1개만 잠갔다.
  이 페이지는 **찜·상태·제보·방문기록 CTA까지 5종 이상**을 함께 잠가야 한다.
  안 그러면 이미 없는 항목에 찜을 누른 사용자가 두 번째 막다른 골목을 만난다.
  상세는 상단 정적 링크에 `.focus()`만(새 링크 만들지 말 것),
  **수정은 그 링크마저 죽으므로 `collection.js`처럼 새 "목록으로 돌아가기" 링크 생성.**
- **PATCH 계약**: 폼의 모든 필드를 서버 렌더 값으로 채우고 **제출 시 전부 그대로 보낸다.**
  dirty 추적을 새로 만들지 마라 — 안 건드린 필드는 no-op, 지운 선택 필드는 `""`.
- **사진 삭제 = 즉시 반영** (`PATCH { image: null }`, JSON). 저장소의 다른 모든 단일
  클릭 파괴 동작이 즉시+확인이라 이것만 예외로 두면 확인창 동의와 어긋난다.
- **제보 성공(201)** → 목록이 아니라 **같은 상세 URL로 리로드**.
- `setLoading(btn, false)`가 `lockForm()`보다 **먼저** — bfcache 복원 시 `.is-loading`이
  남으면 전역 pageshow가 잠긴 버튼을 되살린다.
- 필수 항목 미입력 시 `.focus()` **호출한다** — `collection.js`는 안 하고
  `personal_create.js`는 한다. 접근성이 나은 쪽을 따른다.

**기존 것으로 안 되는 것 4가지**: 404 잠금 캐스케이드 확장 / 단일 이미지 삭제
(선례 없음) / 2버튼 고정 바(기존은 전부 1버튼) / 찜·상태·제보 동시 잠금 트리거.

## 구현 중 발견·수정된 결함 (자동 테스트로는 못 잡음)

1. **프로덕션 타임존 결함** — 서버 `strftime`이 UTC를 찍어 00:00~09:00 KST 등록 건이
   전날 표시(하루의 37.5%). 형제 선례가 `DateField`용이라 적용 불가였다. 원본
   datetime + 템플릿 `|date:` 로 전환
2. **찜·상태 404 잠금 미작동** — 공유 `status.js`가 실패를 내부에서 끝내고 이벤트
   미발행 + 응답이 **400**(DRF가 pk를 검증 실패로 처리, 404 아님). 가산적
   `status:request-failed` 이벤트로 해결. **필드명(`personal_entry`)으로 판단하고
   한국어 문자열 매칭 금지**
3. **제보 404 후 삭제 버튼 미잠금** — `lockPageForGoneEntry()`가 소유하도록 이동
4. **제보 경로 안내 문구가 숨겨진 폼 안에 갇힘** — 잠긴 페이지에 설명이 없었다.
   문구 소유권을 `lockPageForGoneEntry()`로
5. **상태 라벨 하드코딩**(드리프트 위험) — PD-12로 vocab 단일화
6. **메타 행 중복 표시** — WED `Deviates`(위 사후 verdict 표 참조)
