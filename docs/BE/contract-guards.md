### core 공용 모듈 가드 — 기본 거부, 예외 0건 (2026-08-02부터)

**2026-07-31 상태(기본 거부 + 허용 목록 2개)는 폐지됐다.** 프레젠테이션 뷰가
`web/views/`로 전부 옮겨간 뒤로는 `core/**/*.py`가 도메인 앱을 임포트할 정당한
이유가 하나도 남지 않는다 — `core`는 커널이고, 화면 조립은 `web`이 한다. 그래서
허용 목록 자체를 없앴다: `core`가 `archive`/`events`/`drafts`를 임포트하면 그건
예외가 아니라 항상 위반이다. 이 전환의 선행 조건이던 예외 두 건(`core/views/`
패키지, `core/promotion.py`)은 **둘 다 파일 자체가 `web/`로 옮겨져 사라졌다** —
남겨서 허용할 필요가 없어진 게 아니라, 허용할 대상 자체가 없어졌다.

R1(`test_core_공용_모듈은_도메인_앱_모듈을_임포트하지_않는다`)은 이제 예외 없이
`core/**` 전체를 스캔한다. 빈 위반 목록이 "스캐너가 살아서 못 찾은 것"인지
"스캐너가 죽어서 빈 것"인지 그 자체로는 구분되지 않으므로, 합성 트리
(`core/anything.py = "import archive.models"`)에 같은 스캔 표현식을 돌려
여전히 잡아낸다는 양성 대조를 별도 테스트로 남겼다
(`test_core_스캔_경로에서_도메인_임포트가_있으면_R1이_실제로_잡는다`).

⚠️ **아래는 2026-07-31 허용 목록 시절의 실측이다 — 보존.** 도메인 3앱과 달리

(migrations 제외 **28개 파일**):

그래서 당시엔 **기본 거부 + 허용 목록**이었다. `core/**`를 전부 스캔하고 예외는 둘뿐:

## 마크업 리터럴 단언 — 리네임 취약성

**`not in` 형태만 위험하다.** `in` 형태는 리네임하면 즉시 시끄럽게 실패한다.

실측: `class=` 단언 37개 중 `not in`은 8개였고, 그중 **실제로 회귀를 놓친 것은 1개**
(컬렉션 빈 상태), **이미 공허한 것 2개**(저장소에 없는 문자열),
나머지 5개는 양성 단언·`aria-label`·앵커 개수 가드가 짝을 이뤄 안전했다.

**새로 쓸 때의 규칙**: "없음"을 단언하려면 **스타일 클래스가 아니라 안정 앵커**를
써라 — 접근 이름(`aria-label`), `href`, 폼 필드명. 클래스 리터럴은 리네임 한 번에
"존재하지 않는 문자열의 부재"를 검사하게 된다.

⚠️ **앵커 유일성은 페이지 단일 템플릿에서 세지 마라.** 렌더 결과는 `base.html`과
partial이 합쳐진 것이다. `<form`을 앵커로 골랐다가 `_topbar.html`의 로그아웃 폼
때문에 실패한 사례가 있다.

## `tests/core/test_secret_literal_guard.py` — 테스트 시크릿 리터럴

**배경**: GitGuardian이 테스트 파일의 리터럴 비밀번호·자격증명 URI로 PR을 실패시킨
사례(PR #275)가 있었고, 기존 규약(`valid_password` 픽스처의 secrets 런타임
조립, ci.yml 저엔트로피 런타임 생성)이 조언 산문뿐이라 재발했다.

**잡는다**: ① 이름에 "password"가 포함된(대소문자 무시, `db_password`류 포함)
kwarg 또는 할당에 4자 이상 문자열 상수 — 단, 값이 `/`로 시작하는 URL 경로
상수는 예외 ② `스킴://사용자:비밀번호@호스트` 형태와 매치되는 문자열 상수.
스캔 대상은 `git ls-files` 기준 `tests/` 아래 모든 `.py`(가드 파일 자신 포함).

패턴①의 이름·길이·경로 예외는 최초 버전(정확히 `password`, 8자 이상)이
PR #316에서 GitGuardian에 재탐지된 뒤 실측으로 좁힌 지형이다 — GitGuardian
Generic Password 탐지기는 이름에 "password"가 **포함**되면 4자 값도 잡고,
URL 경로 상수·dict 폼 데이터 키는 미탐지였다.

**못 잡는다**: f-string(`JoinedStr`)으로 조립한 값 — `ast.Constant`가 아니므로
스캔 밖이다. 이것이 허용된 회피 관례의 근거다: 자격증명 URI가 필요하면
비밀번호 조각을 `secrets.token_hex(4)` 같은 런타임 호출로 만들어 f-string으로
조립하고(변수명이 `password`류를 포함해도 값이 리터럴이 아니면 안전), 비밀번호
자체가 불필요하면(`force_login` 등) `password=None`을 쓴다.

⚠️ **GitGuardian은 AST가 아니라 원시 텍스트를 스캔한다.** 이 가드 파일 자신의
캐너리·단위 픽스처 문자열에 `password…='값'` 연속 패턴이나 완전한
`스킴://u:p@h` URI를 그대로 적으면, AST 스캔 범위 밖(문자열 리터럴 내부)이라
가드 자신은 통과해도 GitGuardian 원시 텍스트 스캔에는 걸린다(PR #316 실측 —
password 이름에 8자 값을 대입하는 캐너리 문자열이 재탐지됨). 그래서 픽스처
문자열은 `.format()` + 문자열 덧셈으로 런타임에만 조립하며, 이 문서 자신도
같은 이유로 걸리는 형태의 원문 인용을 남기지 않는다.

**한계**: 변수 참조 kwarg(`password=some_var`)나 비-리터럴 조립은 애초에
문자열 상수가 아니라 잡을 대상이 아니다 — 우회가 아니라 설계상 제외다.

## 이 저장소에서 반복되는 실패 유형

- **기대값이 전부 0인 단언은 무방비다.** 새 dict 키를 상수 `0`으로 박아도
  519건이 통과한 사례가 있다(이벤트 카탈로그 트랙).
- **통과는 증거가 아니다.** 가드를 고쳤으면 **깨뜨려서 Red가 되는지**와
  **깨끗한 상태에서 Green인지**를 **둘 다** 재라. 한쪽만 재서 잘못된 앵커가
  통과한 사고가 있었다.
- **뮤테이션 판정은 종료 코드로만 하라.** stdout에서 `failed`를 문자열로 찾으면
  AXES 로그의 "failed login attempts"를 테스트 실패로 오독한다.
- **동시 실행 간섭**: 사용자가 같은 저장소에서 작업 중이면 pytest가 겹쳐
  전체 스위트가 거짓 에러를 낸다(3 errors → 재실행 시 정상). 단발 실패를
  결함으로 보고하기 전에 재실행하라.
