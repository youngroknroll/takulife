Integrated Planning Document v2

OshiLog MVP 통합 기획 문서 v2

오타쿠·서브컬처 팬을 위한 행사 정보 탐색 및 방문 기록 서비스의 통합 기획 문서입니다. 이번 버전은 기존 “관리자 수동등록”의 운영 부담을 줄이기 위해 URL 기반 행사 초안 생성 + 관리자 검수/승인 방식을 핵심 데이터 전략으로 반영했습니다.

서비스: 덕질 캘린더 + 기록장 핵심 니즈: 정보 + 인증·기록 초기 범위: 서울/수도권 등록 방식: URL 기반 반자동 초안

1. 최종 요약

OshiLog는 애니·게임·서브컬처 팬이 팝업스토어, 콜라보카페, 극장특전, 굿즈예약 같은 덕질 일정을 확인하고, 관심 있는 일정을 저장한 뒤, 실제 방문 경험을 사진과 메모로 기록하는 웹 서비스입니다.

최종 MVP 정의

서울/수도권 서브컬처 팬이 공식 링크가 있는 덕질 행사를 확인하고, 관심 있음·방문 예정·다녀옴·놓침 상태로 관리하며, 다녀온 경험을 개인 기록장에 남길 수 있는 웹 MVP. 행사 데이터는 완전 수동등록이 아니라 공식 URL 기반 초안 생성 + 관리자 검수/승인 방식으로 운영합니다.

정보 니즈

흩어진 팝업·콜라보·특전 정보를 한 곳에서 확인

저장 니즈

관심 있는 행사를 방문 예정으로 관리

인증 니즈

다녀온 행사 사진과 후기를 남김

운영 니즈

관리자가 URL만 넣고 초안을 검수

핵심 판단

  • 커뮤니티가 아니라 개인 덕질 아카이브로 시작한다.
  • 행사 정보는 유입을 만들고, 방문 기록은 재방문을 만든다.
  • 완전 수동등록은 지속 불가능하므로 URL 기반 반자동 초안 생성을 MVP에 포함한다.
  • 자동 게시가 아니라 관리자 검수 후 게시를 원칙으로 한다.
  • 공식 이미지/SNS 이미지는 무단 저장하지 않고 카테고리 기본 썸네일을 사용한다.

2. 시장 니즈 분석

오타쿠·서브컬처 시장에서 강한 니즈는 단순한 커뮤니티 참여보다 최애 소비, 행사 정보 탐색, 굿즈 구매, 방문 인증, 개인 기록 쪽에 있습니다. 이 중 OshiLog의 1차 MVP는 정보 니즈와 인증·기록 니즈에 집중합니다.

2.1 정보 니즈

  • 이번 주 진행 중인 팝업스토어를 알고 싶다.
  • 내가 좋아하는 작품의 콜라보카페 일정을 놓치고 싶지 않다.
  • 극장 특전, 굿즈 예약, 공식 이벤트 마감일을 확인하고 싶다.
  • 공식 링크, 장소, 기간, 예약 여부를 한 번에 보고 싶다.

2.2 인증·기록 니즈

  • 다녀온 팝업스토어와 콜라보카페를 기록하고 싶다.
  • 방문 사진, 굿즈 구매 내역, 대기 시간, 후기를 남기고 싶다.
  • SNS에 흘러가는 기록이 아니라 개인 아카이브로 쌓고 싶다.
  • 월별·작품별로 덕질 활동을 돌아보고 싶다.

2.3 운영 니즈

행사 데이터는 계속 바뀌고, 출처는 여러 곳에 흩어져 있습니다. 운영자가 행사명, 날짜, 장소, 요약을 매번 직접 입력하면 MVP 단계에서도 피로도가 높습니다. 따라서 운영자에게 필요한 것은 “입력 도구”가 아니라 초안 생성 도우미입니다.

방식장점단점판단
완전 수동등록 정확도 통제 가능 운영 부담이 너무 큼 초기 소량 시드 외에는 부적합
완전 자동 크롤링 속도 빠름 정책·저작권·오정보 리스크 큼 MVP에는 부적합
URL 기반 반자동 초안 운영 부담 감소 + 품질 통제 가능 검수는 여전히 필요 OshiLog MVP 추천 방식

3. 서비스 포지셔닝

OshiLog는 단순한 행사 정보 사이트도, 오타쿠 커뮤니티도 아닙니다. 핵심 포지셔닝은 덕질 일정 발견과 개인 기록을 연결하는 아카이브 서비스입니다.

하지 않을 것

초기 커뮤니티 자체 거래 무단 크롤링 공식 이미지 무단 저장 자동 게시

초기 MVP에서는 운영 리스크가 큰 기능을 의도적으로 제외합니다.

할 것

행사 목록 상태 저장 방문 기록 내 기록장 URL 초안 생성

사용자가 혼자 써도 가치 있고, 운영자도 지속 가능한 개인 도구로 시작합니다.

핵심 문장

정보 니즈는 첫 방문을 만들고, 인증·기록 니즈는 재방문을 만든다. 운영 측면에서는 URL 기반 초안 생성이 행사 데이터 공급의 지속 가능성을 만든다.

4. 타깃 사용자

초기 타깃은 모든 오타쿠가 아니라 오프라인 행사 참여 가능성이 높은 서울·수도권 서브컬처 팬입니다.

팝업 탐색형

행동: 이번 주 갈 만한 팝업과 콜라보카페를 탐색

불편: 정보가 SNS와 공식 사이트에 흩어져 있음

필요: 지역·날짜·분류 필터, D-Day

일정 저장형

행동: 가고 싶은 행사를 캡처하거나 메모장에 저장

불편: 방문 예정 관리가 어려움

필요: 관심 있음, 방문 예정, 놓침 상태 관리

최애 기록형

행동: 다녀온 행사 사진과 후기를 남김

불편: SNS 기록이 흘러가고 정리되지 않음

필요: 방문 기록장, 월별 타임라인

5. MVP 범위

첫 버전은 작게 가되, 운영 지속성을 위해 URL 기반 행사 초안 생성 기능은 포함합니다. 검증해야 할 핵심은 사용자가 행사 목록을 보고 저장하고, 실제 방문 후 기록까지 남기는지입니다.

5.1 MVP 1차 범위

URL 기반 행사 초안 생성 관리자 초안 검수/게시 행사 목록 행사 상세 관심 있음 방문 예정 다녀옴 놓침 방문 기록 내 기록장

5.2 초기 행사 카테고리

포함보류보류 이유
팝업스토어생일카페팬 주최가 많고 공식성·검수 기준이 복잡함
콜라보카페동인행사/온리전운영 정책과 제보 검수 부담이 큼
극장특전팬 주최 행사출처 신뢰성과 일정 변경 이슈가 많음
굿즈예약일반 전시 전체서브컬처 특화성이 약해질 수 있음

5.3 MVP 제외 범위

댓글 DM 팔로우 자체 거래 완전 자동 크롤링 자동 게시 결제 앱 푸시 복잡한 추천 알고리즘

9. 데이터 수집 전략 v2

행사 목록 데이터는 완전 수동등록도, 완전 자동 크롤링도 아닙니다. OshiLog의 MVP 데이터 전략은 URL 기반 행사 초안 생성 + 관리자 검수/승인입니다.

수정된 데이터 전략

관리자는 공식 URL을 입력하고, 시스템은 HTML 텍스트에서 행사 정보 후보를 추출합니다. 추출 결과는 EventDraft로 저장되며, 관리자가 검수·수정·승인한 뒤에만 Event로 게시됩니다.

9.1 데이터 확보 흐름

1
URL 입력

공식 행사 URL 입력

2
본문 추출

title/meta/body 일부 추출

3
후보 추출

제목·날짜·장소 후보 생성

4
초안 저장

EventDraft로 저장

5
검수 게시

관리자 승인 후 Event 게시

9.2 반자동 추출 대상

추출 항목방법주의
raw_titleHTML title, og:title, h1정확도 높음
raw_textmeta description, 본문 일부너무 길게 저장하지 않음
날짜 후보정규식 기반 패턴 추출자동 확정하지 않고 후보로 표시
장소 후보키워드 또는 AI 후보 추출관리자 확인 필수
요약 후보본문 일부 기반 요약초기에는 직접 수정 전제
이미지저장하지 않음저작권 보호를 위해 기본 썸네일 사용

9.3 왜 자동 게시하지 않는가

  • 행사 날짜와 종료 조건은 출처마다 표현 방식이 다르다.
  • “소진 시 종료”, “추후 공지”, “예약 필수” 같은 예외가 많다.
  • 잘못된 정보가 올라가면 사용자가 직접 피해를 본다.
  • 오타쿠 행사 정보는 신뢰가 중요하므로 최종 검수는 사람이 해야 한다.

9.4 초기 데이터 범위

항목초기 기준
지역서울/수도권 중심. 특히 홍대, 합정, 성수, 여의도, 용산
카테고리팝업스토어, 콜라보카페, 극장특전, 굿즈예약
등록 수오픈 전 30~50개, 이후 주간 10~20개 업데이트
출처공식 링크가 있는 행사만 게시
이미지공식 이미지를 저장하지 않고 카테고리별 기본 썸네일 사용

10. 행사 초안 생성 도우미

행사 초안 생성 도우미는 관리자용 기능입니다. 목표는 운영자가 모든 필드를 직접 입력하는 것이 아니라, 시스템이 만든 초안을 검수하도록 만드는 것입니다.

11.4 계산값 처리

D-Day, 예정, 진행 중, 종료 같은 값은 DB에 저장하지 않고 날짜 기준으로 계산합니다.

@property
def progress_status(self):
    today = timezone.localdate()

    if self.start_date > today:
        return "예정"

    if self.end_date and self.end_date < today:
        return "종료"

    return "진행 중"

12. 운영 정책

12.1 행사 등록 규칙

  • 공식 링크 없는 행사는 게시하지 않는다.
  • EventDraft는 자동 게시하지 않는다.
  • 관리자 승인 전까지 Event 목록에 노출하지 않는다.
  • 날짜가 불분명한 행사는 DRAFT 또는 PENDING으로 둔다.
  • 종료일이 불명확하면 “소진 시 / 추후 공지”로 표시한다.
  • 본문은 직접 요약하거나 초안 요약을 수정한다.
  • 공식 이미지는 무단 저장하지 않는다.
  • 행사 대표 이미지는 카테고리별 기본 썸네일을 사용한다.
  • 사용자가 방문 기록에 직접 올린 사진만 저장한다.

12.2 이미지 정책

이미지 저작권 주의

MVP에서는 공식 이미지, SNS 이미지, 포스터 이미지를 임의로 다운로드해 저장하지 않습니다. URL 기반 추출에서도 이미지는 저장 대상에서 제외합니다. 행사 목록은 카테고리별 기본 그라디언트 썸네일을 사용하고, 실제 사진은 사용자가 자신의 방문 기록에 직접 업로드한 경우에만 저장합니다.

12.3 검증 지표

지표의미
행사 목록 조회 수정보 탐색 니즈가 있는지 확인
행사 상세 클릭률카드 정보가 상세 확인으로 이어지는지 확인
관심 저장률사용자가 단순 조회를 넘어 개인화 행동을 하는지 확인
방문 예정 전환율서비스가 실제 행동 계획으로 이어지는지 확인
기록 작성률OshiLog의 기록장 방향이 유효한지 확인하는 핵심 지표
초안 생성 성공률URL 기반 등록 도우미가 운영 부담을 줄이는지 확인
초안 수정 소요 시간완전 수동등록 대비 얼마나 효율적인지 확인

13. 개발 로드맵

지금 당장 개발한다면 아래 순서로 가는 것이 현실적입니다.

1순위
Event 모델 + 행사 목록/상세

게시된 행사 데이터를 사용자 화면에 보여준다.

2순위
EventDraft + URL 기반 초안 생성

관리자가 URL을 넣으면 초안을 만들고 검수할 수 있게 한다.

3순위
관리자 승인 워크플로우

EventDraft를 승인하면 Event로 변환해 게시한다.

4순위
UserEventStatus

관심 있음, 방문 예정, 다녀옴, 놓침 상태를 사용자별로 저장한다.

5순위
VisitRecord + 내 기록장

사진 업로드, 한줄 후기, 만족도, 월별 타임라인을 제공한다.

6순위
EventSubmission

사용자 제보를 URL 기반으로 받고 EventDraft로 전환한다.

7순위
AI 추출 보조

규칙 기반 추출이 안정화된 뒤 AI JSON 추출을 보조 기능으로 추가한다.

추천 기술 스택

  • Backend: Django
  • DB: PostgreSQL
  • Frontend: Django Template + HTMX + Alpine.js
  • Style: Bootstrap 5 또는 Tailwind
  • Parser: httpx 또는 requests + BeautifulSoup
  • Date Extraction: 정규식 기반 후보 추출
  • Image: 사용자 방문 기록 사진만 저장. S3 호환 스토리지 또는 Supabase Storage
  • Deploy: Render
  • Admin: Django Admin + 커스텀 관리자 액션

14. 자체 검토 결론

이전 버전에서는 데이터 품질을 위해 관리자 수동등록을 제안했지만, 운영 지속성 관점에서 완전 수동등록은 부담이 큽니다. 따라서 이번 버전에서는 URL 기반 행사 초안 생성 + 관리자 승인을 MVP에 포함하는 방향으로 수정했습니다.

이전 판단수정 판단이유
관리자 수동등록URL 기반 초안 생성 + 관리자 검수운영 부담을 줄이면서 데이터 품질을 지키기 위해
사용자 제보는 후순위후순위 유지, 단 URL 기반 제보로 설계사용자에게 긴 폼을 요구하면 제보율이 낮아지기 때문
자동 크롤링 보류완전 자동 크롤링은 계속 보류정책, 저작권, 오정보 리스크가 크기 때문
이미지는 카테고리 썸네일유지공식 이미지 무단 저장 리스크를 줄이기 위해
최종 구현 방향

공식 URL 입력 → 시스템이 행사 정보 후보 추출 → EventDraft 생성 → 관리자가 검수/수정 → 승인 시 Event 게시 → 사용자가 관심/방문예정/다녀옴 상태 저장 → 방문 기록 작성 → 내 기록장에서 회고.

포트폴리오 관점의 강조 포인트

  • 행사 정보와 사용자 상태를 분리한 설계
  • EventDraft와 Event를 분리한 검수 기반 운영 워크플로우
  • URL 기반 반자동 초안 생성으로 수동 운영 부담 감소
  • 관심 있음, 방문 예정, 다녀옴, 놓침의 상태 전이 관리
  • 방문 기록과 사용자 업로드 이미지 처리
  • 공식 출처 기반 데이터 품질 정책
  • 자동화보다 검증과 승인 흐름을 우선한 MVP 설계 판단

이력서용 요약 문장 초안

흩어진 서브컬처 행사 정보를 사용자의 관심 상태와 방문 기록으로 연결하는 덕질 아카이브 서비스를 설계했습니다. 초기 MVP에서는 완전 수동등록의 운영 부담과 자동 크롤링의 리스크를 모두 고려해, 공식 URL 기반 행사 초안 생성과 관리자 검수/승인 워크플로우를 도입했습니다. 사용자는 행사를 관심 있음·방문 예정·다녀옴·놓침 상태로 관리하고, 방문 후 사진과 후기를 개인 기록장에 남길 수 있도록 구성했습니다.
